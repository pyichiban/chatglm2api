# 生图（文生图 / 参考图改图）协议与实操

> 合并自 `IDE生图协议分析.md`（2026-09-30）与 `生图OpenAI兼容接口可行性评估.md`（2026-10-14），
> 两者已删除。本文档保留**仍然有效**的结论，剔除过时/被推翻的内容，并补 2026-10-15 的线上复核。
>
> 证据来源：`ref/chatglm_ide_20260930.saz`、`temp/saz2`（WEB 抓包）、
> 以及 2026-10-15 的线上实测脚本（均在 `temp/`，gitignored）。
> 标注：`[实证]` = 抓包/实测直接证据；`[未知]` = 无证据。

## 1. 一句话结论

| 能力 | 端点 | 状态 |
|---|---|---|
| **文生图** | `POST backend-api/assistant/stream` + `assistant_id=65a232c082ff90a2ad2f15e2` + `meta_data.cogview` | ✅ 可用（2026-10-15 复核：5/5 成功，一次 4 图，12.5~14.7s） |
| **参考图改图** | `POST drawing-api/v1/image/reference` | ✅ 可用（**只需一个上游可达的公网图片 URL**，不需要上传接口） |
| 参考图上传 | `POST productivity-api/file/chat_upload` | ❌ **当前被 WAF 拦死**（不带 `refer__991` 时 100% 40012）——但**可完全绕开**，见 §3.2 |
| **多图输入** | —— | ❌ **不支持**：`image/reference` 是单图接口，画图 agent 也忽略对话里的图片项；多角色请合并到**一张**参考图，见 §3.7 / §3.8 |

**没有独立的「创建生图任务」接口**：文生图就是普通对话通道换 agent + 参数，产物在 SSE 里逐张推回。

## 2. 文生图（走普通对话通道）

### 2.1 请求

```
POST /chatglm/backend-api/assistant/stream      (SSE, IDE 指纹)
assistant_id = 65a232c082ff90a2ad2f15e2         (AI画图智能体)
meta_data.cogview = {aspect_ratio, style, scene, chat_model, rm_label_watermark}
```

请求体与普通对话的差异**只有两处**：`assistant_id` 与 `meta_data.cogview`（普通对话只有
`{"rm_label_watermark": false}`，生图多出 `aspect_ratio/style/scene/chat_model`）。

> 本项目 `GlmClient.generate_image()` 已封装；`meta_data.platform` 本库写死 `"pc"` 而头部指纹是 `win`，
> **服务端不校验该一致性**，不影响出图 `[实证 2026-10-15]`。

### 2.2 SSE 响应：6 帧 / 一次 4 图

```
帧0  top=init   part=init    content=[{type:"text", text:""}]                    ← 空文本占位
帧1-4 top=init  part=finish  content=[{type:"image", code:"<润色后prompt>",
                                       image:[{image_url:"..._<n>_0.jpg"}]}]      ← 每图一个独立 part
帧5  top=finish part=finish  content=[{type:"one_to_more_finish", image:[{}]}]   ← 收尾
```

| 项 | 值 |
|---|---|
| 图帧的 `part.status` | **`finish`**（不是 `init`；`logic_id = <history_id>_<n>`）`[实证 10-15]` |
| 润色后的实际生图 prompt | 在**同一个 `image` 内容项的 `code` 字段**（4 张各一份，互不相同）；**不存在** `type:"code"` 的项 |
| `image[]` 元素 | 只有 `image_url` 一个键 |
| 末帧 | `type:"one_to_more_finish"`、`image:[{}]`（空对象，聚合时跳过） |
| 顶层 `meta_data` | `answer_type:"multi"`、`cogview.generate_image_type:1`、`meta_data.total_time`（**在 meta_data 里**，顶层无此键） |
| 耗时 | 12.5~14.7s（4 图）；抓包记录 16.1s |
| 产物直链 | `https://sfile.chatglm.cn/testpath/<history_id>_<n>_0.jpg`，**无需签名**可直接 GET |
| 格式转换 | URL 加 `?image_process=format,png` → **真 PNG**（实测 1024×1024 / 415KB） |

**⚠️ 流末尾还有一行不带 `data:` 前缀的裸 JSON 信封**：
`{"status":0,"message":"success","result":null,"rid":"..."}`。
`iter_sse_data()` 会忽略它（行为正确），但 `stream=True` 原样透传会把它带给下游
⇒ **做 OpenAI 兼容层时必须过滤** `[实证 10-15]`。

### 2.3 `aspect_ratio` 实测映射（2026-10-15 全集）

| `aspect_ratio` | 产物尺寸 |
|---|---|
| `1:1` | 1024×1024 |
| `3:4` | 864×1152 |
| `4:3` | 1152×864（预设列表里没有，但上游接受） |
| `9:16` | 720×1280 |
| `16:9` | 1280×720 |
| `21:9`（非法） | **1024×1024** —— ⚠️ **静默降级为 1:1，不报错** |

⇒ 兼容层必须自己校验/归一化 `size`，不要指望上游拒绝非法值。

### 2.4 `style` / `scene` 已失效 `[实证 10-15]`

传配置里的真实枚举（`style=van_gogh`、`scene=logo_design`），出图与 `none` **无肉眼差异**
（仍是通用写实/摄影风）⇒ 上游只按 `aspect_ratio` 路由，这两个参数可透传但**不要承诺效果**。

### 2.5 其它实测

- **不扣积分**：`left_score` 生图 5 次前后均 330.00 `[实证 10-15]`。
- 连续生图（间隔 6~8s）**不触发 40012**。
- 产物右下角带「清言·AI生成」角标（`rm_label_watermark=false` 时）；去水印取值 `[未知]`。
- **删会话不回收图**：`bulk_delete` 后产物直链仍可下载（靠 `history_id` 不可枚举保密）。

## 3. 参考图改图（智能编辑）

### 3.1 请求

```
POST /chatglm/drawing-api/v1/image/reference      (JSON, 同步长请求 ~17~22s)
```

```json
{
  "image_url": "<公网可访问的图片 URL>",     // ← 唯一必需输入，见 §3.2
  "file_id": "",                             // 可留空；传旧 ID 也无所谓
  "type": "Intelligent Editing",             // 固定
  "category": 1,
  "conversation_id": "", "history_id": "",
  "assistant_id": "65a232c082ff90a2ad2f15e2",
  "prompt": "<编辑指令>",
  "if_plus_model": false,
  "title": "【智能编辑】 " + prompt前40字,     // 前端约定，建议照抄
  "aspect_ratio": "1:1",                     // ⚠️ 无效，见 §3.3
  "rm_label_watermark": true
}
→ {"status":0,"message":"success","result":{"image_url":"https://sfile.../<hash>_0.jpg",
                                            "conversation_id":"..."}}
```

### 3.2 ⭐ 不需要上传接口：`image_url` 接受任意上游可达的公网 URL `[实证 10-15]`

| `image_url` 形式 | 结果 |
|---|---|
| `https://sfile.chatglm.cn/...`（自家 CDN，无签名） | ✅ status=0，17.9s |
| `https://img0.baidu.com/it/...`（境内公网图床，**原图直接用**） | ✅ status=0，20.6s |
| `https://cdn.jsdelivr.net/gh/...` / `ghproxy.net/https://raw.githubusercontent.com/...` | ✅ status=0（境外代理，能过） |
| `https://raw.githubusercontent.com/...`（直连境外） | ❌ status=500（上游拉不到） |
| `data:image/jpeg;base64,...`（内联 data URI） | ❌ status=500 |
| `https://raw.gitmirror.com/...` | ❌ status=10031「不支持该图片」 |

⇒ **只要图在一个上游服务器能拉到的公网 URL 上，就能直接做参考图改图**，
`file_id` / `chat_upload` 都不需要。参考图不必裁切、不必转换格式。

> 兜底托管方案（无自有图床时）：临时公开仓库 + `ghproxy.net` 中转。
> 实测可行（上游 22.6s 正常出图），用完把仓库转私有并删文件即可。
> 注意 `ghproxy` 有几分钟 Fastly 边缘缓存，删文件后短时间内 URL 仍可能 200。

### 3.3 ⚠️ 编辑模式**强制保持输入图比例** `[实证 10-15]`

`aspect_ratio` 传值与输出无关，输出比例 = 输入比例：

| 输入 | 传 `aspect_ratio` | 输出 |
|---|---|---|
| 890×500（1.780） | `1:1` | **1760×992（1.774）** |
| 600×600（1:1） | `1:1` | 1312×1312 |
| 512×512（1:1） | `1:1` | 1312×1312 |

⇒ 想要正方形构图，必须**先把参考图补白成 1:1**（补背景色，不要裁切，避免裁掉角色）。

### 3.4 角色一致性验证（提示词对照法）

用提示词里**故意不写**的特征来反证模型是否真的读到了图：

- 参考图：薇斯纳角色卡（金发精灵耳 + 半透明蝶翼 + 蓝白礼服 + 发光法杖）。
- 提示词只写「发色、发型、头饰严格遵循参考图」，**不写"金发"**，也不写法杖、翅膀缎带。
- 产物：金发蓝眼、法杖、蝶翼缎带全部自动带上；参考图左侧的中文文案与排版**没有被画进成品**。
  ⇒ 模型确实读到了参考图的**角色**语义，而不是整张卡面 `[实证 10-15]`。

### 3.5 历史坑：`chat_upload` 被 WAF 单独拦死

```
POST /chatglm/productivity-api/file/chat_upload     (multipart: file + from + assistant_id)
```

- 2026-09-30/10-14：间歇性 40012（密集重试会加重，冷却 ~7min 后单发可过）`[抓包]`。
- **2026-10-15：不带 `refer__991` 时 100% 40012**（win 与 pc 两种指纹、233KB PNG 与 31KB JPEG 均被拒，
  秒拒 0.09~0.58s；冷却 2h25m 后单发仍失败）。同刻 `recent_list`（写）200、
  `image/reference`（写）正常 ⇒ **不是账号级频率限流，是这条 multipart 路径被 WAF 规则单独拦**。
- 抓包佐证：IDE 客户端的画图面板是 webview，画图那一族请求**都带 `refer__991`**
  （`chat_upload` 1/1、`image/reference` 1/1、`drawing/config` 2/2、连生图那条 `assistant/stream` 也带），
  而主对话窗口的请求不带 ⇒ 这条路径本就受更严校验。
- **结论：不要再依赖 `chat_upload`**。要么走 §3.2 的公网 URL，要么注入新鲜
  `refer__991`（库已支持 `Credential.refer_991` / `GLM_REFER_991`，`_url()` 会自动拼接）。

### 3.6 已排除的弯路（试错记录，避免重复踩）

| 尝试 | 结果 | 结论 |
|---|---|---|
| `image_url` 传 data URI（base64 内联） | status=500，1.05s | 上游不认内联数据 |
| 用普通对话接口把 base64 塞进 prompt，让模型"看图" | 模型只会去**沙箱跑解码代码**（还因工具轮数耗尽失败），并自陈「我无法真正看到这张图」，连 JPEG 尺寸都报错 | **不可行**：文本通道拿不到视觉理解 |
| 换 WEB(`pc`) 指纹传 `chat_upload` | 仍 40012（`rid` 全 0） | 与指纹无关 |
| 用更小的图（31KB）传 `chat_upload` | 仍 40012 | 与体积无关（抓包 185KB 反而成功过） |
| 从会话历史回捞旧上传图的 URL | `page_messages_v2` 返空 list；`backend-api/conversation/messages` 404；`v1` 版 `status=1 invalid_request_error` | 走不通 |

### 3.7 ❌ 多图输入：**不支持**（三条独立证据）`[实证 10-15]`

先澄清一个容易混淆的点：**「能读图」与「能拿图作画」是两件事，取决于 agent**。

| agent | 能否读 `messages[].content[].type=="image"` | 输出 | 实测 |
|---|---|---|---|
| 主对话 `65940acf…` | ✅ **能读**，且可多图、可多轮累积 | 只有文本 | 无图时答「看不到图片」；给图后准确答出金发/尖耳/星形法杖/「薇斯纳」；多轮无图追问仍记得，并可同时回顾两张图 |
| 画图 `65a232c0…` | ❌ **完全忽略**图片项 | 图片 | 单图/双图/qtype=`image_upload`/加 `special_scene`/多轮传图 **全部不吃参考图**，产物是模型自己编的（狐/虎/柴犬/柯基），只有提示词的**结构**被执行（“并排”“戴帽子”） |

而画图侧唯一的参考图入口 `image/reference` 是**单图接口**，证据：

| 尝试 | 结果 |
|---|---|
| `image_urls` / `images` / `image_list` / `file_ids` 并列字段（含不可达 URL 做探针） | 全部 `status=0` 正常出图 ⇒ **这些字段被直接忽略**（上游只读 `image_url`） |
| `image_url` 传 JSON 数组 | HTTP 400 `invalid param` |
| `image_url` 用 `,` / `\|` / `;` / 空格 拼接两个 URL | 全部 `status=10031「不支持该图片」`（0.3~2s 秒回）⇒ 整串被当成**一个** URL |
| 单值不可达 URL（对照组） | `status=10031`（1.34s）⇒ 证明上游确实去拉了图，**失败会秒回**，因此上面“成功”的用例确实是“字段没被读” |

> 附带发现：`status=10031「不支持该图片」` 是一个很实用的**探测信号** —— 上游拉不到图会 1~2s 秒回，
> 而正常出图要 17~22s。可以用它快速判定“某个字段是否被上游读取”，不必等出图。

**前端代码旁证**：JS 里确有 `t.push({type:"image", image: e.img_list})`（`img_list` 是数组），
上传控件也允许 `fileList.length >= 10` —— 但那个数组是发给**主对话通道**的；
画图面板走的是另一条路（`image/reference` 单值）。
又：配置里那条“疯狂动物城融合”的 feed 提示词写的是“将**人物主体**与兔子朱迪融合”，
需要的是「1 张用户图 + 1 张内置素材」，与单图接口自洽。

### 3.8 ✅ 多角色参考图的正确用法：**把多角色放进同一张参考图**

既然接口只收单图、画图 agent 又不读图片项，想要“两个角色同框”就应把**多个角色合并到一张参考图**
（角色设定集 / 角色卡天然就是这样），再用提示词**分别锚定**每人特征。

实测（《女神异闻录5》双人设定集，1011×1280 竖版）：

| 项 | 结果 |
|---|---|
| 输入 | 双角色设定集（含左侧色卡、日文色号表、多处头部特写） |
| 输出 | 1152×1472，18.87s，无可见水印 |
| 角色一（伊織順平） | 藏青棒球帽+徽章、深棕西装+紫衬衫敞领、腰带、短胡茬、项链 —— 全对 |
| 角色二（桐条美鶴） | 酒红长卷发、白衬衫、橙色蝴蝶结领结、黑 A 字裙、及膝长靴（靴口皮带+金扣）—— 全对 |
| 互动 | 男性一手插兜、一手抬起做说话手势；女性双手身前轻握、侧头看他 —— 按提示词执行 |
| 忽略 | 色卡 / 日文文字表 / 标题 / 头部特写**都没被画进成品** |

提示词要点（可复用模板）：

1. 开头就声明“**只把图中两位角色的形象作为身份依据，忽略色卡、文字、排版、色号表格等一切非角色元素**”；
2. 用「角色一（男性，图中上方）」「角色二（女性，图中下方）」**分块**描述，每块列 3~5 条硬特征
   （发型发色 / 帽子 / 服装配色与款式 / 鞋靴 / 神情），并明确“图中位置”帮助模型定位；
3. 互动写成**可执行的动作指令**（谁的手放在哪、看向谁、气氛如何），而不是抽象形容；
4. 声明“身高差与参考图一致”“各自身份特征完整可见”；
5. 构图比例按 §3.3 预期 —— 输出会跟随参考图比例（竖版设定集 → 竖版成品）。

> 优于“客户端先拼图”：设定集里的角色本就是**同一画风、同一画布**，模型对“这是两个独立角色”的理解更准；
> 拼图方案容易被模型当成“一个整体画面”来处理。

## 5. 封成 OpenAI 兼容接口的可行性

下游契约（调用方自行构造，非官方 SDK）：`POST {BASE}/images/edits` + multipart 重复字段 `image[]`。

| 字段 | 上游现状 | 可行性 |
|---|---|---|
| `model` | 需别名映射到 AI画图智能体 | ✅ |
| `prompt` | 直接对应 | ✅ |
| `size` | 上游只认比例 | ⚠️ 需映射表（§2.3） |
| `quality` | **无对应参数** | ❌ 忽略 |
| `output_format: png` | CDN `image_process=format,png` **真转换** | ✅ |
| `background: transparent` | **无透明能力** | ❌ 建议显式 400 报错，别静默忽略 |
| `image[]`（多图） | 上游**只收 1 张**（`image_url` 单值） | ❌ 需兼容层合成（Pillow 拼图；长边 ≤1024、<4MB；语义损失要告知） |
| `Authorization` | 可用同一 key 做网关鉴权 | ✅ |

**响应**：下游期望 `{"created":..., "data":[{"b64_json":"..."}]}`。
产物 CDN 直链会过期且不可缓存，需下载后 base64；`revised_prompt` 可取文生图 SSE 里的
`content[].code`（参考图改图路径没有该字段）。

**架构**：glm2api 目前是纯客户端库（仅依赖 `requests`，无 HTTP server），
要兼容 `/images/*` 需新增一层薄 server。

### client 能力（已实现）

```python
client.generate_image(msg, aspect_ratio="1:1", style="none", scene="none", **opts)
    # 文生图（走对话通道换 agent）；图片以 Markdown 形式混在返回的 text 里
client.edit_image(prompt, image_url, *, file_id="", rm_label_watermark=True, **opts)
    # 参考图改图 → {image_url, conversation_id}
    # image_url 必须是上游可达的公网 URL；输出比例跟随输入图
    # ⚠️ 单图接口（多图不支持，见 §3.7）；多角色请合并到同一张参考图（§3.8）
```

常量（已加入 `glm2api/constants.py`）：

```python
EP_IMAGE_REFERENCE = "/chatglm/drawing-api/v1/image/reference"
EDIT_TYPE_INTELLIGENT = "Intelligent Editing"
EP_FILE_UPLOAD = "/chatglm/productivity-api/file/chat_upload"   # ⚠️ 当前被 WAF 拦，勿依赖
```

> 实现细节：`edit_image()` 走 `_raw_request()`（不接 40012 退避）——实测该端点不限流，
> 且长请求（~17~22s）在 `READ_TIMEOUT=60` 内；响应仍是 `{status,message,result}` 信封。
>
> 待办（可选）：可给 `edit_image()` 加一个 `images=[...]` 参数，**内部自动拼图**后再传单图，
> 以免调用方误以为多图会被上游接受（上游是静默忽略，不会报错）。

### 实现注意

- **超时**：编辑端点 17~22s，需放宽读超时（现有 `READ_TIMEOUT=60` 够用）。
- **清理**：生图/编辑都会产生会话，用 `delete_conversations(..., assistant_id=ASSISTANT_DRAWING)`
  删除（用主对话 ID 删会**静默无效**）`[实证]`。
- **图片 URL 有效期**：编辑产物直链无签名但会过期，不要缓存 URL，建议立即下载。
